# ADR 0004: Document storage abstraction

**Status:** Accepted

**Context.** Claimants and officers attach supporting documents. Binary files shouldn't live in database columns, and the assessment environment has no object store.

**Decision.**
- Metadata lives in `claim_documents`: type, display name, detected content type, size, SHA-256 checksum and storage key.
- Content goes through the `FileStorage` interface. For now there's one implementation, `LocalFileStorage`, which writes to a mounted volume.
- Keys are generated by the server (`claims/<claimId>/<uuid>`), and paths are resolved strictly inside the storage root.
- The file type is validated from its leading bytes (PDF, PNG or JPEG) and the size is capped at 10 MB.
- If the transaction rolls back, the stored file is deleted.

**Consequences.**
- An S3 or Azure Blob adapter can replace the local one without changing `DocumentService`.
- While storage is a ReadWriteOnce volume, the backend Kubernetes Deployment runs a single replica. Moving to object storage removes that limit.
- Virus scanning is not implemented; it would hook in before the metadata is persisted.
